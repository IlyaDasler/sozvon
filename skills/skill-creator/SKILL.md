# Skill Creator

Навык для создания навыков и их итеративного улучшения.

## Общий цикл

1. Понять, что навык должен делать и как.
2. Написать черновик `SKILL.md`.
3. Придумать 2–3 реалистичных тестовых промпта.
4. Прогнать их с навыком и без него (baseline).
5. Дать человеку посмотреть результаты и собрать обратную связь.
6. Переписать навык по feedback и по замерам.
7. Повторять, пока результат не устроит; затем расширять набор тестов.
8. В конце — оптимизировать `description` для срабатывания.

Гибкость важнее ритуала: если человек говорит «просто сделай без прогонов», делаем без прогонов.

## Как общаться

Пользователи очень разные. По умолчанию можно говорить «проверка», «замер», «сравнение».
Слова «JSON», «assertion», «grader» — только если видно, что человек в теме; иначе коротко объяснить.
Не перегружать терминами; лучше показать результат, чем описать процесс.

## Анатомия навыка

```
skill-name/
├── SKILL.md            # обязателен: frontmatter + инструкции
├── scripts/            # детерминированные повторяемые операции
├── references/         # документы, читаемые по необходимости
├── assets/             # шаблоны, картинки, шрифты
└── evals/              # тестовые кейсы
```

`SKILL.md` — до ~500 строк. Всё длинное выносить в `references/` и ссылаться по ситуации.
В `description` — и что делает навык, и когда его применять: это главный механизм срабатывания.
Писать чуть «настойчивее» обычного: современные модели склонны недоприменять навыки.

## Стиль инструкций

- Императив, но с объяснением «почему» — модель умная, ей нужен смысл, а не набор MUST.
- Общее важнее узкого: навык будет использоваться тысячи раз на разных запросах.
- Никаких выдуманных путей, API и файлов. Всё, что упоминается, должно существовать.
- Не включать вредоносный код и не помогать с несанкционированным доступом.

## Тестовые кейсы

2–3 реалистичных промпта, как сказал бы живой человек. Сохранять в `evals/<case-name>/`:

```
eval-case/
├── prompt.md
├── case.yaml
├── graders/          # по одному файлу на проверку
└── files/            # входные файлы, если нужны
```

Старый формат `evals/evals.json` не трогать; новые кейсы — только папками.

## Прогон и оценка

Результаты складывать в `<skill-name>-workspace/iteration-N/`:

```
iteration-1/
├── case-name/
│   ├── eval_metadata.json   # prompt + assertions
│   ├── with_skill/outputs/  # + grading.json + timing.json
│   └── without_skill/       # baseline
├── benchmark.json
└── benchmark.md
```

1. Запускать with-skill и baseline **в один заход** (параллельно, если есть субагенты).
2. Пока идут прогоны — писать проверки: объективные, с понятными названиями, о результате
   («summary.md содержит выручку 693.5»), а не о месте сохранения.
3. Для каждого завершённого прогона сразу сохранять `timing.json`:
   `{total_tokens, duration_ms, total_duration_seconds}` — эти данные больше нигде не появятся.
4. Оценивать каждый прогон по проверкам, писать `grading.json` с полями
   `text`, `passed`, `evidence`.
5. Собирать `benchmark.json`/`benchmark.md`: pass rate, время, токены, mean ± stddev, delta.
6. Открывать человеку `eval-viewer/generate_review.py` (в headless — `--static`), а не
   показывать сырые файлы. Вкладки: «Outputs» (кейсы и обратная связь) и «Benchmark».
7. Читать `feedback.json`, улучшать навык, повторять итерации; указывать `--previous-workspace`.

Субъективные навыки (стиль, дизайн) оцениваются человеком; не натягивать на них формальные проверки.

## Улучшение навыка

- Обобщать feedback, а не подгонять под один пример.
- Убирать из промпта всё, что не приносит пользы; читать транскрипты, а не только результат.
- Если несколько прогонов писали один и тот же скрипт — вынести его в `scripts/`.
- Объяснять «почему»; жёсткие ALWAYS/NEVER — сигнал переписать мягче.
- Сравнивать версии можно «слепым» способом: два результата независимому агенту без имён.

## Оптимизация description

1. Сгенерировать 20 реалистичных запросов: 8–10 «должно сработать», 8–10 «не должно»,
   причём отрицательные — близкие по смыслу, а не очевидно чужие.
2. Дать человеку проверить набор (HTML-шаблон) и утвердить.
3. Запустить цикл оптимизации (`run_loop`), смотреть train/test, брать `best_description`
   по test-оценке, а не по train.
4. Показать «до/после» и цифры, обновить frontmatter.

## Упаковка

Если есть инструмент показа файлов — собрать `.skill` и отдать человеку.
При обновлении существующего навыка сохранять его имя и путь; копировать в записываемое место.

## Правила проекта «Созвон»

Этот навык применяется и к нашей разработке: любой новый процесс, проверка или
вспомогательный навык оформляется по этой схеме — с тестовыми кейсами и замерами,
а не «на глаз». Для переноса Go-бэкенда используется отдельный навык
`sozvon-go-parity` (см. `skills/sozvon-go-parity/SKILL.md`).
